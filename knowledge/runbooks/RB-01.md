# Payment error spike

## Signal and scope
This runbook applies to the local `payments` demo service. Symptoms: HTTP 5xx, rejected charges and failed checkout. Record the alert start time, affected requests, current release, and related services before suggesting a cause. Treat this document as guidance, not authorization to change a live system.

## Investigation
Likely cause to test: Payment handler returns exceptions or upstream processor rejects requests. Inspect payment error ratio and gateway 5xx; compare processor responses; pause retries if they amplify errors; escalate to payment owner. Link each observation to its Prometheus query, trace, backup job, or incident number. Compare the signal against a healthy interval; a coincident deploy alone does not prove causation.

## Recovery and verification
Any state-changing step requires a human-approved change request. Error ratio returns below baseline and test checkout succeeds. Record the exact time, owner, and evidence after verification. If the expected recovery does not occur, reopen the hypothesis and escalate.
