# Incident severity

## Signal and scope
This runbook applies to the local `gateway` demo service. Symptoms: Multiple service alerts with differing user impact. Record the alert start time, affected requests, current release, and related services before suggesting a cause. Treat this document as guidance, not authorization to change a live system.

## Investigation
Likely cause to test: Shared dependency or separate incidents. Count failed user requests and affected services; assign severity using impact and duration; record why severity changed. Link each observation to its Prometheus query, trace, backup job, or incident number. Compare the signal against a healthy interval; a coincident deploy alone does not prove causation.

## Recovery and verification
Any state-changing step requires a human-approved change request. Severity matches observed scope. Record the exact time, owner, and evidence after verification. If the expected recovery does not occur, reopen the hypothesis and escalate.
